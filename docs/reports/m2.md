## 確認できた事実

- Mediabunny の `Conversion`（`composable: true`、`audio: { discard: true }`、`copy: { mode: 'forced' }`）で映像はパケットのままコピーされる。ffmpeg でパケットを抽出した MD5 が入出力で一致し、フレーム数・解像度・ビットレートも同じ。コピーできない場合は `utilizedTracks` に映像が入らないので、`ExportError('video-copy')` にして再エンコードはしない。
- **AAC エンコーダーの遅延**：`@mediabunny/aac-encoder`（FFmpeg の AAC）は 1024 サンプルのプライミングをタイムスタンプに反映しないため、そのまま出すと音声が 21.33 ms 遅れた。対策として、音声を `AudioSampleSource` で明示的なタイムスタンプ（開始 = −遅延）で渡すと、Mediabunny がエディットリスト（`elst`）を書き、再生側がプライミングを飛ばす。遅延は「エンコード→多重化→デコード」を 0.5 秒の信号で実測して決め（`measureEncoderDelay`）、デコードできない環境では AAC 1024 / Opus 0 を使う。実測後の同期誤差は 0.00 ms。
- **Opus in MP4 の先頭**：ffmpeg が作った Opus 入り MP4 はプリスキップ（312 サンプル）をエディットリストで表すため、Mediabunny は最初のサンプルを −6.5 ms と報告するが、WebCodecs の Opus デコーダーはすでにプリスキップを捨てている。負のオフセットをそのまま使うと 6.1 ms 早くなった。Opus は先頭を 0 とみなすようにした。AAC は負のオフセット（プライミング）を捨てる扱いを維持（AAC 入力の実機確認が必要）。
- **MP3 入力**：Mediabunny / WebCodecs は LAME ヘッダーのギャップ情報を使わないため、ffmpeg のデコードより 1105 サンプル（23 ms）長い先頭になる。音声のみの入力では同期の相手がないので実害はないが、README の既知の制限に書く。
- Chromium（Playwright 同梱）は H.264 / AAC をデコードできないため、AAC 入力のエラー経路（`undecodable-audio`）と、音声なし（`no-audio`）、音声 2 トラック（1 本目を処理）の挙動を確認した。H.264 の映像コピーはデコード不要なので Chromium でも検証できた。

## 計測結果（6 秒・1280×720・30 fps の試験メディア、ヘッドレス Chromium）

| 入力 | 出力 | 映像パケット | 音声 | 同期（先頭 / 末尾） |
|---|---|---|---|---|
| H.264 + PCM（MOV） | MP4 + AAC 128 kbps | 一致（MD5） | AAC 48 kHz 2ch | 0.00 / 0.00 ms |
| H.264 + Opus（MP4） | MP4 + AAC 143 kbps | 一致 | AAC | 0.00 / 0.00 ms |
| H.264 + Opus 縦 720×1280 | MP4 + AAC | 一致 | AAC | 0.00 / 0.00 ms（補正前） |
| VP9 + Opus（WebM） | WebM + Opus 128 kbps | 一致 | Opus | 0.00 / 0.00 ms |
| 音声 2 トラック（MP4） | MP4 + AAC | 一致 | 1 本目を処理 | 0.00 / 0.00 ms |
| WAV 44.1 kHz | WAV 16-bit | — | 一致 | 0.00 / 0.00 ms |
| MP3 48 kHz | WAV 16-bit | — | 先頭 23 ms 長い（LAME ギャップ情報） | — |
| H.264 + AAC / M4A | エラー `undecodable-audio`（Chromium のみ） | — | — | 実機で確認 |

- 書き出し時間は 6 秒の動画で 0.5 秒（AAC ポリフィル）、WebM で 0.07 秒。
- 出力の音声は AAC のフレーム境界まで 768 サンプルほど長くなる（末尾のパディング。再生に影響なし）。
